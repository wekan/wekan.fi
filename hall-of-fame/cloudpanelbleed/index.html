CloudPanelBleed 2026-11-22 xet7 Found while reworking the Cloud Panel into a separate Cloud Admin container; fixed by xet7.

The Cloud Panel could be turned on from the browser: any site administrator of any WeKan could set the Cloud Panel Domain and its SuperAdmin in Admin Panel / People / Cloud, and then save a customer domain with a MongoDB host, port and credentials of their choosing. The server connected to that database to test it and to import from it. On a host where every customer runs their own WeKan container and is its administrator, that let a customer make their WeKan reach MongoDB servers on the internal network and read from them.

The Cloud Panel now exists only when the server has the environment variable CLOUD set to its domain, typically in a separate Cloud Admin container. It cannot be set or changed from the browser or the API, and a value stored in the database has no effect. Every Cloud Panel method, and the one place that connects to a database from given credentials, refuses without it, and the attempt is shown in Admin Panel / Problems. The Cloud Admins are that container's administrators; a Cloud Admin may be limited to chosen IPv4 and IPv6 addresses, and the Cloud address has no REST API for requests without a login.

CWE-918, CWE-284. High severity. Fix prepared locally for the Upcoming release; not yet released.

Details

The Cloud Panel keeps many customer domains, each with its own WeKan container and MongoDB database, and holds those databases' passwords so it can test them and merge them into one WeKan. Until this fix its domain and SuperAdmin were set from the browser, in Admin Panel / People / Cloud, by any site administrator - also of a customer's own WeKan, where the customer is the administrator.

Fix

cloudDomainFromEnv() in models/lib/cloudPanel.js is the only source of the panel's domain: the CLOUD environment variable. requireCloud() in server/cloudPanel.js is called by every Cloud Panel method before its argument checks, and by withSource(), the one place that builds a MongoDB client from given credentials. The People / Cloud settings pane is gone, and the methods that set the domain always refuse. The Cloud Admins are the container's site administrators; Admin Panel / Cloud may limit them to chosen addresses, and the Cloud address answers no REST API request without a login.

Detection

A Cloud Panel method called on a WeKan without CLOUD, a Cloud Admin from an address that is not allowed, and an unauthenticated REST request at the Cloud address are summarized as CloudPanelBleed in Admin Panel / Problems.

Verification

tests/cloudPanelGate.test.cjs fails when any MongoClient is built from data that is not the server's own environment outside the gate; tests/cloudPanelAccess.test.cjs runs the real methods and login handler with and without CLOUD; a Playwright spec checks there is no Cloud tab or pane without CLOUD, even with a domain stored in the database, and the whole panel with it.
