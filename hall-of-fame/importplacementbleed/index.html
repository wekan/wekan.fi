ImportPlacementBleed 2026-10-29 Zachariah Mithani (AploSec)

Reported by email, with a proof of concept and a suggested fix. Asked to add it as a GitHub security advisory too; it has not arrived there yet, so three stars for now (no GHSA, suggested fix present). When the GHSA arrives, the CVE is requested through it and the stars become five.

An import into a board the importer may write was placed beside a list, swimlane or card id taken from the request without checking that it belonged to that board, so cards were created on one board pointing at another board's list and swimlane, and a card id of another board could be probed. CWE-639; medium severity. No CVE assigned. Fix prepared locally for the Upcoming release; not yet released.

Details

An export can be imported INTO a board that is already open, beside the swimlane, list or card whose menu was used (#1173). Two routes reach that scoped importer: POST /api/import/zip?boardId=..., which takes the swimlane, list and card as swimlaneId, listId and cardId query parameters, and the importScoped method, which takes them in its target. Both authorized the import on the board alone - the caller must be able to write it - and checked the other three ids only for their format.

The importer then placed the cards with them as given: a listId and swimlaneId went onto every new card as its list and swimlane, and a cardId was looked up with no board filter, its list and swimlane used in the same way. So a writer of board A could create cards on A whose list and swimlane were those of board B, a board they are not a member of - cards that show in neither place as they should, and that views selecting by list id may draw under B's list. The cardId variant also answered whether a card id existed anywhere. The REST card create already refuses a list or swimlane of another board (#6572).

Fix: before anything is written, the importer looks the list, swimlane and card up together with the id of the board it imports into (models/lib/importPlacement.js decides, ScopedImporter._checkPlacement looks up). An id that is not on that board is refused - 400 listId does not belong to this board. over REST, error-import-placement from the method - with the same answer for a card of another board and a card that does not exist, so it is no longer a probe. The cards are placed only by what was found on the board, never by a raw id from the request.

Detection

A refused import is recorded as ImportPlacementBleed in Admin Panel / Problems (key authz.import-placement), with the route it came by. The account is not blocked: an import menu left open while its list was moved to another board reaches the same refusal. Logging can never break the refusal.

Verification

tests/importPlacementBleed.test.cjs drives the decision with the reporter's ids, checks that the importer looks every target id up on the board before it writes, and fails if any target id is written onto a card or looked up without the board. tests/playwright/specs/security-import-placement.e2e.js runs the reporter's attack against a running server by both routes - zip and method, list and swimlane, foreign card and missing card - and expects 400, no card planted, and the record in Admin Panel / Problems, then imports beside the board's own list and card. It passes in Chromium and Firefox and fails on the previous code.
