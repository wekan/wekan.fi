Details

InviteBleed — CWE-330 Insufficiently Random Values + CWE-307 Excessive Auth Attempts

when public registration is disabled, invitation registration used a 6-digit code generated with Math.random() (~900,000 keyspace, non-cryptographic RNG; server/models/settings.js) with no throttling on the sign-up validation, so an attacker who knew a pending invitee's email could brute-force the code, claim the account and join its private boards. Fixed by generating a 128-bit crypto.randomBytes invitation code and rate-limiting createUser with DDPRateLimiter.

Reported privately by meifukun (https://github.com/meifukun), who reviewed 8 issues against WeKan v9.95.0 (commit f602b9459fa1622f60ee8c3b639f02035f3ab32b) on local self-hosted instances only. Fixed at the upcoming WeKan release.

Follow-up fix, 2026-11-20

The same report later arrived as GitHub Security Advisory GHSA-rg85-qx5c-qx67, and checking it against the current code found two things the first fix left. An invitation created before the fix, and not used yet, kept its six-digit code and was still accepted at sign-up - a re-invite even mailed the same code again. And the DDPRateLimiter rule was on createUser, which a client is refused anyway, while the sign-up form creates the account through ATCreateUserServer, which had no limit. Now a code shorter than the 22 base64url characters of a 128-bit code is refused at sign-up and replaced by a strong one on a re-invite (models/lib/invitationCodeEmail.js isStrongInvitationCode), and ATCreateUserServer takes at most 10 attempts a minute per address, each refusal counted in Admin Panel → Problems under InviteBleed.
