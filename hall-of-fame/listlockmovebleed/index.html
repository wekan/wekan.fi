CVE requested

ListLockMoveBleed 2026-11-22 adityasunny06help-coder

Coordinated disclosure via GitHub Security Advisory GHSA-394w-8q99-q4qx, with the affected lines, an end-to-end proof of concept against the official v13.27 bundle and a suggested fix; validated and fixed by xet7.

When a board admin refused a role write access in one list (roleExceptions, #4527), a normal member could still move the whole swimlane holding that list's cards to another board with POST /api/boards/:boardId/swimlanes/:swimlaneId/move: the route asked only for write access to the two boards, and the cards landed in lists on the other board with no exceptions, where the member could edit or delete them.

CWE-862, CWE-863. Medium severity (CVSS 6.5). CVE requested. Affected v13.04 through v13.27. Fix prepared for the Upcoming release.

Details

A board admin can give a list its own rule for a role (list.roleExceptions, #4527): for example, Normal members may read a list but not write in it. Since 2026-11-18 that refusal also covers deleting, archiving and moving a swimlane that holds cards in the list, and every path enforced it but one. The Meteor method moveSwimlane asks assertSwimlaneListsWritable, the REST swimlane delete asks assertSwimlaneListsNotRefused, and client writes meet the Swimlanes deny rule. POST /api/boards/:boardId/swimlanes/:swimlaneId/move asked only for write access to the source and destination boards. Moving a swimlane moves its cards: for each list, swimlane.move() finds or creates a list of the same title on the destination board and moves the cards into it, and those lists carry no exceptions. So a normal member refused by the list, with an API token, could move the swimlane to another board they belong to, and then edit or delete the locked list's cards there. It is the same shape as ListLockBleed and ListLockBulkBleed: one path of a family left asking only for board-level write access.

Fix: the REST move asks assertSwimlaneListsNotRefused in server/lib/listPermissionGate.js for every list holding the swimlane's cards, or bound to it, before swimlane.move(), and answers 403 and moves nothing when one refuses the caller's role. As for the other REST routes, only a list's refusal counts, and the board admin, whom no list exception binds, is unaffected.

Found with it: the reporter noticed that every REST swimlane move, an allowed one too, answered 500 after its first card had already moved: the card move read Meteor.userId() for its position history, which throws on the server outside a Meteor method. The mover is now read without throwing, so a REST move of a swimlane or a card completes instead of stopping half done.

Detection

A refused move is recorded in Admin Panel / Problems as ListLockMoveBleed (key authz.list-locked-move, source rest:swimlane-move). The board's menu does not offer the move to such a member, so only a direct API call reaches the refusal. Medium severity in Problems: it never disables the account. An allowed move records nothing.

Verification

tests/listLockStructure.test.cjs runs the gate on a board with a list refusing normal.write and checks that the move is refused with 403 and recorded under ListLockMoveBleed, with the negative cases of an open swimlane, the board admin and a missing swimlane. It pins that the move route asks the gate before swimlane.move(, and scans every server file for a swimlane move( whose handler does not ask the gate first, so the same mistake cannot return on another path. tests/cardMoveOutsideMethod.test.cjs pins the card move's guarded read of the user. tests/playwright/specs/list-lock-move.e2e.js replays the report against a running server: the member's move to board B is refused and every card stays on board A, the board admin moves it, and the same member moves a swimlane with no refusing list with 200, every card arriving on board B.
